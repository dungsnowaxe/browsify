Browsify — Technical Specification & Rust Architecture Plan

A standalone, ultra-lean Rust successor to Finicky for macOS (with a cross-platform core). Engineered for < 6 MB RSS memory, sub-5 µs declarative URL routing, < 1 µs cached browser profile resolution, 0 MB idle UI overhead, and 100% drop-in compatibility with Finicky v3/v4 configurations.

Target RAM: ~4.5–5.7 MB RSS (550 KB dirty anon) Hot Path: 2.35 µs (Native) / 42.5 µs (QuickJS) JS Runtime: rquickjs (QuickJS-ng, dropped when static) Config UI: On-Demand 127.0.0.1 Browser UI (0 MB idle) Compatibility: Finicky v3, v4 (.js/.ts) & rules.json
Sections: 1. Empirical Benchmarks 2. Competitive Deep Dive (Grinch & Finch) 3. Rust Workspace Architecture 4. Browser & Profile Engine 5. Finicky Compatibility & Migration 6. On-Demand Localhost UI 7. Test Parity & Finicky Issue Matrix 8. Phased Implementation Plan

Why Current Finicky Uses 100–200 MB RAM & 17+ ms Per Click

Memory Culprits in apps/finicky/src/

  • goja-babel (+146.8 MB RSS spike): configfiles.go:196 calls babel.Init(1), loading a 2.6 MB babel.min.js compiler into a Goja VM pool solely for transform-named-capturing-groups-regex.
  • 320 KB finickyConfigAPI.js inside Goja: Bundles core-js URL polyfills and zod into the Goja interpreter even for simple JSON rules.
  • Eager WebView Asset Allocation & Leaky Window: window.go:73 (init()) copies all Svelte UI assets into Objective-C NSMutableDictionary buffers at boot; window.m:68 sets [window setReleasedWhenClosed:NO], keeping WKWebView alive forever once opened.

Latency Culprits on Every URL Click

  • Per-Click Zod Schema Validation (6.8 MB / 109k allocs): packages/config-api/src/index.ts:84 runs ConfigSchema.parse(config) inside openUrl() on every single click.
  • Uncached Local State Parsing (3.66 MB / 7.5 ms): launcher.go:205 reads and unmarshals Chrome's multi-MB Local State JSON into map[string]interface{} on every click.
  • Unconditional Accessibility IPC & /usr/bin/open Fork: main.m:289 queries AXUIElementCopyAttributeValue for windowTitle even when no rule uses it; launcher.go:97 forks /usr/bin/open and blocks on pipes.

2. Existing Rust & Native Alternatives — Deep Dive & How Browsify Improves on Them

Source-Level Analysis of Grinch (Rust) & Finch (Swift)

We audited the source code of the two closest modern alternatives: jamtur01/grinch (a Rust + objc2 + macOS JavaScriptCore router) and expelledboy/finch (~650 LOC Swift + JavaScriptCore). While both validate the compiler-first native routing approach, Browsify improves on them across six architectural dimensions:

1. Lower Memory via Ephemeral QuickJS 5.1 MB vs 15.5 MB

  • Grinch links macOS JavaScriptCore and holds a live Retained<JSContext> in LoadedConfig for the entire lifetime of the process (~15.5 MB RSS), even when 100% of rules are declarative.
  • Browsify Improvement: Uses rquickjs (~550 KB dirty RAM) and drops the JS runtime completely after config load whenever all rules/rewrites compile to native Rust matchers (~4.5 MB RSS).

2. Smarter Profile Cache mtime + Typed Serde

  • Grinch (src/chromium.rs:64) parses Chrome's entire Local State into a heap-heavy serde_json::Value tree, never checks file mtime (requiring manual "Reload Config" if profiles change), and caches transient read failures as permanent empty maps.
  • Browsify Improvement: Deserializes only profile.info_cache.*.name via a zero-waste typed serde struct (659 µs cold) and auto-invalidates via (mtime_ns, size) stat check (0.87 µs warm).

3. True Finicky v3/v4 Compatibility Zero Breakage

  • Grinch changes bare string semantics ("github.com" matches subdomains in Grinch vs exact URL in Finicky), rejects .finicky.ts, fails on import / named exports, throws TypeError on finicky.getPowerInfo() and finicky.notify(), and drops rules.json & short-URL expansion.
  • Browsify Improvement: Preserves 100% of Finicky v4 & v3 semantics, auto-loads ~/.finicky.{js,ts} and rules.json, and ships browsify migrate.

4. Profile Window Focus & Spaces Fix Issues #501 & #550

  • Both Finicky (open -n) and Grinch (setCreatesNewApplicationInstance(true)) spawn a transient second browser process when passing --profile-directory. When that helper forwards IPC to the running browser and exits, macOS often fails to focus the target window or switches to the wrong Space.
  • Browsify Improvement: Performs explicit post-handoff window activation and supports Chrome PWA --app-id & Arc Space routing.

5. Visual Rules UI with 0 MB Idle RAM Best of Both Worlds

  • Finicky keeps a heavy WKWebView in memory forever; Grinch and Finch deleted the GUI entirely (CLI only).
  • Browsify Improvement: Keeps the rich packages/finicky-ui Svelte interface (Rule Builder, URL Tester, Profile Picker, Log Viewer), served on-demand over 127.0.0.1:0 in the user's browser with 0 MB idle RAM.

6. Cross-Platform Core & CI Testability Linux + macOS

  • Grinch and Finch tightly couple their JS engine to Apple's Objective-C JavaScriptCore, making their core config/routing engine impossible to compile or test on Linux CI.
  • Browsify Improvement: browsify-core, browsify-js, and browsify-ui-server are 100% platform-agnostic Rust + rquickjs; only browsify-macos touches objc2.

The Hybrid Compiler + Ephemeral QuickJS Execution Model

Case A: Purely Declarative Config (~4.5 MB RSS · 2.35 µs/URL)

  1. User has rules.json, browsify.toml, or a ~/.finicky.js whose rewrite and handlers entries use wildcard strings, arrays, regexes, or built-in helpers (finicky.matchHostnames, strip()).
  2. browsify-js evaluates the file once in rquickjs, extracts all rules into native browsify_core::CompiledConfig structs, and drops the rquickjs::Runtime and Context immediately.
  3. Every URL click runs 100% in native Rust with zero JS engine in memory.

Case B: Config with Dynamic JS Functions (~5.1 MB RSS · 42.5 µs/URL)

  1. User's ~/.finicky.js contains custom JS closures, e.g. match: ({ url, opener }) => ... or url: (url) => ....
  2. Static rules ahead of the closure still compile to native Rust matchers (if an earlier native rule matches, JS is never entered!).
  3. Only when evaluation reaches a JS closure does Browsify invoke the compiled function handle inside rquickjs (~550 KB dirty heap).

Fixing the Chromium Multi-Profile Focus & macOS Spaces Bug (Issues #501 & #550)

When a Chromium browser is already running and a link is routed to a specific profile, macOS's NSWorkspace.openURLs ignores command-line arguments. Both Finicky (open -n -a ... --args --profile-directory=...) and Grinch (setCreatesNewApplicationInstance(true)) work around this by spawning a second instance of the browser binary, which passes the --profile-directory argv over Mach IPC to the main browser process and immediately exits. However, because the newly spawned child process exits within milliseconds, macOS drops window activation—causing the link to open silently in the background (#501) or leaving focus on the wrong profile's window across macOS Spaces (#550).

Browsify's 3-Step Profile Launch & Focus Protocol

  1. Fast Path (No Profile / No Custom Args): Calls NSWorkspace.openURLs_withApplicationAtURL_configuration_completionHandler with createsNewApplicationInstance = false and addsToRecentItems = false. LaunchServices delivers the URL directly via AppleEvent to the running browser.
  2. Profile / Custom Args Path: Calls NSWorkspace.openApplicationAtURL_configuration_completionHandler with arguments = ["--profile-directory=...", ..., url] and createsNewApplicationInstance = true.
  3. Post-Handoff Foreground Activation (when openInBackground == false): In the completion handler (once the helper process hands off to the primary browser PID), Browsify locates the primary running NSRunningApplication for that bundle ID and invokes activateWithOptions(NSApplicationActivateAllWindows) so macOS switches to the Space and window where the profile tab just opened.

6. Zero-Idle-RAM Configuration & Rules UI

Reusing packages/finicky-ui Over Ephemeral 127.0.0.1 HTTP

In Finicky v4, apps/finicky/src/window/window.go embeds the built packages/finicky-ui Svelte application and loads it into an in-process WKWebView that never deallocates when closed. Browsify keeps the exact same Svelte UI experience (Start Page, Visual Rule Editor, URL Tester, Browser Profile Selector, Log Viewer) with 0 MB of idle memory:

1. Idle State (0 MB UI RAM)

The resident daemon does not link WebKit.framework and does not copy HTML/CSS/PNG buffers into Objective-C dictionaries at startup.

2. On-Demand Launch

When the user clicks "Rules & URL Tester…" in the menu bar or runs browsify --window, browsify-ui-server binds to 127.0.0.1:0 (random ephemeral loopback port with a one-time session token) and opens it in the user's browser.

3. WebSocket/SSE Bridge & Auto-Stop

A lightweight 20-line shim replaces window.webkit.messageHandlers.finicky with fetch/EventSource calls to the loopback server (supporting testUrl, getRules, saveRules, getInstalledBrowsers, getBrowserProfiles). Once the tab closes, the server shuts down and frees all buffers.

8. Phased Implementation Plan

Execution Sequence

Phase 1: browsify-core (Pure Rust Router & Profile Engine)

  • Scaffold Cargo workspace at repo root alongside existing folders.
  • Implement Finicky-compatible wildcard matcher, regex matcher, hostname matcher, and native URL rewriter.
  • Implement ProfileResolver for Chromium (Local State typed serde + (mtime, size) cache) and Firefox (profiles.ini + Profile Groups SQLite + Containers).
  • Implement rules.json & config.toml loader and short-URL resolver.
  • Port all wildcard, rule, and profile unit tests (`cargo test -p browsify-core`).

Phase 2: browsify-js (QuickJS Runtime, Transpiler & Migration)

  • Embed rquickjs with the FinickyURL, LegacyURLObject, and finicky.* prelude.
  • Add TypeScript type-stripping and ESM export default transformation so ~/.finicky.js and ~/.finicky.ts load directly without Babel or esbuild.
  • Build the hybrid rule extractor that compiles static JS rules into browsify-core and drops the rquickjs::Runtime when no JS functions remain.
  • Implement browsify migrate to inspect and convert Finicky configs.

Phase 3: browsify-macos (AppKit Daemon, AppleEvents & Launcher)

  • Implement objc2 NSApplication delegate (kAEGetURL, openFile:, Handoff, ASWebAuthenticationSession).
  • Implement flock singleton lock, AppNap prevention, lazy AXUIElement windowTitle, CGEventSourceFlagsState modifiers, and IOKit power info.
  • Implement direct NSWorkspace launching with post-launch profile window focus handoff and menu bar status item.

Phase 4: browsify-ui-server & browsify-cli

  • Implement the on-demand 127.0.0.1:0 HTTP bridge serving packages/finicky-ui with automatic idle shutdown.
  • Wire CLI commands: browsify --test <url>, browsify --validate, browsify --list-browsers, browsify --list-profiles, browsify migrate, and browsify --ui.
  • Add build scripts for Browsify.app bundle packaging and end-to-end benchmark suite.
